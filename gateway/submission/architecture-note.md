# Architecture Note

根据学员在实验中的回答整理。

## 1. 工具面与能力边界

安全边界不能交给模型自行判断，因此仅开放查询、读取、创建采购单草稿和提交四项明确能力，不提供能任意选择 ERP 方法的万能工具，也不提供修改供应商付款条件的能力。DocType 使用固定白名单，参数按契约验证；未知工具、白名单外对象、缺失必填字段和多余参数在工具层拒绝，不向 Gateway 转发。万能工具会扩大模型能调用的地址与操作范围；一旦受到提示词注入影响，就可能尝试越权修改业务数据或执行不可逆动作。窄工具与服务端权限、审批检查共同约束这些动作。

## 2. 身份与站点来源

身份、站点和角色由服务端解析平台认证令牌确定，不由模型或请求体声明。请求体出现 siteId、learnerId、persona 等身份字段时直接拒绝，不采信，也不静默忽略后继续处理；请求体伪造 runId 同样拒绝。调用宿主时使用解析所得的 siteId 与 persona，禁止默认站点兜底。测试同时检查 Alice 读不到 Bob 的单据、Bob 能读到自己的单据，防止“全部拒绝”造成假通过。

## 3. FLOOR 的位置与风险规则

FLOOR 应在 Gateway 服务端、Agent 无权修改的执行边界上运行，判断依据是服务端受保护的风险规则，而非 Agent 可修改的本地风险表。本地画像与 FLOOR 合并时只能加严，不能降级。当前规则下，不可逆操作或更换收款方需要审批；涉及金额的草稿不因此自动变成不可逆操作。修改本地表不能解除服务端对提交操作的审批要求。本项目已用本地 mock 验证这一行为；真实部署中的服务端隔离、权限配置及审批服务是否正确生效，仍需独立实测，冻结 JavaScript 对象本身不等于部署安全边界。

## 4. 业务语义幂等键

建草稿的键由 intent（业务意图）、supplier（供应商）、itemCode（物料编码）、qty（业务数量）和 batch（批次）组成；字符串归一化后按固定顺序拼接。同一业务请求的这些字段稳定，因此重试可得到相同的键；不能包含每次调用都会变化的时间戳、随机数或运行编号。键的去重作用还依赖以身份和站点隔离的持久台账、原子占位和租约归属校验。succeeded 返回原结果，uncertain 不因租约过期而自动重做，必须先对账。
